## 1. 业务目标

### 1.1 两个业务 Dataset、四个覆盖单元

为板块阶段提供以下输入，不扩展成全系统数据源整合工程：

| 业务 Dataset | Industry 覆盖 | Concept 覆盖 | 消费用途 |
|---|---|---|---|
| `sector-ranking` | 已声明行业分类范围内的排行原料 | 已声明概念分类范围内的排行原料 | invest-infra 自行选择板块并评分 |
| `sector-constituents` | 所需行业板块的完整成分 | 所需概念板块的完整成分 | 形成可追溯成分快照，供后续阶段使用 |

这是**两个 Dataset × 两类覆盖**，不是已经决定拆成四个 Dataset。默认 key 不变；不得将“只覆盖 Concept”解释成完成全部业务覆盖。

本计划继续冻结 owner 个人、非商业投资研究参考用途：不向团队提供数据服务，不对外分发原始数据，不形成商业数据产品。自动化采集、内部留存和研究处理的使用条件须有与该场景匹配的来源证据；用途声明本身不替代来源条款、权限与配额核证。[S1]

成功交付是：**一条获准的采集路径，在明确分类、单位、时点、身份和样本范围下，形成可重放的两个业务输入及板块影子结果，并取得 Gate B2A 验收。**数据准入不证明策略收益有效，也不自动生成正式 Candidate。

## 2. 核心原则

1. **先证明可行，再实现接入。**复用既有贡献矩阵，每轮优先关闭一个候选路径的具体缺口；候选优先级不等于正式入选。
2. **统一业务含义，不统一采集生命周期。**WorkBuddy Connector 与内部 Provider 保留各自请求、尝试、归档和权限边界。
3. **业务选择只有一个实现位置。**板块范围裁定、排序、Top-N、同分处理和评分属于 invest-infra；采集端执行数据请求，不解释或复制策略。
4. **可信输入不是“字段齐全”的同义词。**来源、分类、单位、时点、身份和完整度均须有明确检查责任；不能确认时 fail closed。
5. **复用优先，重构有条件。**保留 `evaluate_sector_bundle()`；只有实际接入或已确认的业务校验缺口需要时，才调整内部结构，不因选中某条路径就自动建抽象。
6. **数据准入与策略治理各有权威。**本计划负责来源及输入链；策略主线负责规则、审核、版本和对应 evaluator。两者以固定 artifact 和测试交接，不复制审批体系。
7. **原始证据、规范化输入和运行结果不混淆。**映射、筛选与结果 hash 必须可追溯；重放读取归档，不重新联网冒充原输入。
8. **范围收敛不降低准入要求。**不使用假身份、猜测单位、日期补写、缺数置零或未经授权的规则收窄来“跑通”。

## 3. 最小多源语义

### 3.1 默认复用 1.0，Gate 只选择一条执行路径

原 DS-0M 已记录 WorkBuddy DataRequest/DataBundle 1.0 对多语义 Dataset 与 Dataset 内单成功来源的表达充分，本修订不默认重开协议 2.0。[S1][S5]

| 入选路径 | 最小实现 | 明确限制 |
|---|---|---|
| WorkBuddy Connector | 复用 DataRequest/DataBundle 1.0、既有 codec、候选 Definition 和 evaluator 入口 | `DataAcquisitionDefinition` 只描述该路径；不塞入内部 Provider |
| 单一内部 Provider | 复用 `ProviderRequest → ProviderAttempt → ProviderBatch`；只适配一个获准 Provider | 不伪造 `producer="workbuddy"`，不增加跨 Provider 自动 fallback |

“单一路径”限制本轮交付的执行方式，不强迫 WorkBuddy 的所有 Dataset 来自同一个 Connector。每个 Dataset 内只接受一个最终成功来源，不允许把多个成功响应合并后伪装成一次成功。

默认业务输出仍为 `sector-ranking`、`sector-constituents`。共同基线的 `b0c5493` 已兼容 `sector-ranking`、`sector-constituent-memberships`、`sector-constituent-symbol-map` 三个采集 Dataset，内部关联成 canonical `sector-constituents`，并保留旧二 Dataset 入口。两个业务输入与三个采集输入不矛盾；不因数量不同重写已有 join 或升级协议。该组合是已有实现的复核对象，不是本补丁新批准的生产路径；来源、分类、时点、稳定证券身份及完整度仍按 DS-FM/B2A 验收。

### 3.2 fallback、union、corroboration

| 行为 | 本轮处理 |
|---|---|
| `fallback` | 仅复用获准 WorkBuddy Connector 的既有同口径切换；分类、时点或范围不兼容时不得兜底。单一 Provider 失败后停止；人工改源使用新的获准请求/运行 |
| `union` | 仅在入选路径确实需要多个语义独立输入时，在板块专用内部逻辑组装；不同分类不得按名称拼接，不预建通用组装器 |
| `corroboration` | 可选运行诊断；只有同分类、同时点且真实上游独立时才作为有效旁证；不平均、不覆盖主输入，不设为默认运行依赖 |

Connector、SDK 或访问地址不同，不自动证明上游来源独立。预先定义的关键冲突必须阻断，不能由 AI 决定哪个字段“看起来更可信”。

### 3.3 何时才另行评审 2.0

只有新证据同时证明：同一逻辑记录必须使用多个来源的字段、不能合理拆成语义独立 Dataset、确实需要字段级 lineage、而 1.0 无法安全审计表达时，才另行评审 2.0。

不同版本字段名称、增加数据源、内部函数复用或需要附带诊断记录，都不是自动升级理由。小范围参数/扩展调整也须先核对既有合同允许范围，禁止向严格校验的 DataRequest 偷加字段。

## 4. 最小设计

### 4.1 候选 Definition、影子运行与正式发布

仅在 WorkBuddy 入选时生成候选 Definition；仅在 Provider 入选时配置对应的候选运行路径。候选通过明确 artifact 引用与 hash 使用，不加入 active catalog，不对外宣称已准入。

历史 `sector-strength-ranking/1.0.0.json` 仍绑定策略 v2.0.0，并要求 `zgb`。[S7] 本修订不改写它的身份。目标 v2.1.0 的字段、profile、版本和 artifact hash 必须来自策略主线；不能因为来源缺 `zgb` 就静默移除必需字段，也不能以 scoped profile 代替正式新版本身份。

影子运行允许按显式授权使用已审核、未激活的目标 artifact；只写验收所需归档和结果，不写正式 Candidate，不推进策略 active 状态。生产入口须验证入选来源、适用 Dataset/分类和策略身份与批准范围一致；获准 Connector 枚举本身不等于该 Dataset 已生产准入。最小守卫复用现有入口和批准记录，不新增审批平台。

### 4.2 evaluator 内部收敛：保留入口，只拆必要职责

`evaluate_sector_bundle()` 保留为 WorkBuddy 兼容入口。入选路径应形成如下职责顺序，而不是强制新增同等数量的模块：

```text
采集及原始证据归档
  → 对应采集合同校验
  → 单位/分类/身份/时间/完整度的确定性核验与归一化
  → invest-infra 执行唯一的板块选择规则
  → 取得或提取所需成分，绑定同一份排行输入
  → 确定性评分
  → 可追溯的 SectorStageResult
```

沿用纯计算与外部 I/O 分离。仅当必要时抽取私有 `SectorDatasetSnapshot` 或少量函数；该名称是原计划中的内部结构候选，不是本次冻结的新公共 API。来源适配器不复制评分，计算核心不接收网络客户端、不读取凭证、不写数据库。

DS-C0 的零代码关闭条件是**现有完整调用链及测试已经满足所选路径的全部必要责任**，而不是“选择了 WorkBuddy”。若验证发现单位、完整度或可信加载存在真实缺口，应局部修复；选择 Provider 也不意味着必须进行无收益的抽象。

既有 `b0c5493` 及其历史验证保留为实现基线。先只读建立“已有证据覆盖／v1.1 新增差异／待定位证据”的对照；已满足且证据仍适用的条目复用，不重复开发。代码调整、回退或后续接入仍须 DS-FM 和独立实施授权，不因本次文档校准自动执行。

### 4.3 按需旁证

优先将来源对比保存在既有运行诊断。可选旁证缺失不降低主输入覆盖要求，也不阻断本来满足合同的主路径。只有重复审计或第二个真实消费者产生明确需求时，才评审正式 `CrossCheckReport`；本轮不预建模型、Schema 和存储。

### 4.4 必须明确的业务输入不变量

以下是 **v1.1 新增的验收要求**，不是对当前代码已经满足条件的声明。

| 不变量 | 实施要求与拒绝条件 |
|---|---|
| Dataset 与覆盖范围 | 声明两个 Dataset 的 Industry/Concept 覆盖、排行全集或获批范围、成分是全量还是指定板块范围。不得以截断列表充当全集；实际范围不明则拒绝 |
| 板块身份 | 排行和成分按已验证的分类命名空间、group、稳定板块代码关联。不同来源同名板块不自动等价；无来源修订号时保留观察快照身份，不编造正式版本号 |
| 证券身份 | 保留稳定代码及必要的交易所/市场命名空间；名称不能单独充当权威身份。既有名称规范化 join 仅为待复核的采集关联实现，必须证明同分类、同时点的一一映射并落到稳定代码；不能仅凭文本匹配宣称已准入。不得丢前导零或靠简称猜股票身份 |
| 单位与数值 | 明确上游单位、目标单位、转换公式及映射版本。成交额输出人民币元、涨跌幅输出百分数时必须真实转换；不以字段重命名代替换算。单位未知、非有限值、非法数值拒绝 |
| 业务时间 | 核对来源实际数据对应日期/时点、分类或成分有效时间、抓取时间和交付时间。Dataset 级日期继承只适用于来源保证单一日期的响应；不能把请求日期填回不明时点的数据 |
| 完整度 | 有可核验的范围、分页终止信息、计数或清单证据；行数与 `sample_count` 一致仅证明自洽，不证明上游完整。所需板块须逐一闭合成分覆盖 |
| 来源 lineage | producer、真实上游、访问路径、请求/尝试、原始 artifact/batch、hash、映射版本可读回；规范化和范围提取不能抹掉原始证据 |
| 重试与冲突 | 沿用各自合同：WorkBuddy 同请求同内容幂等、不同内容冲突；Provider 同逻辑请求可保留新的 attempt/batch 及既有修订，不套用 WorkBuddy 单交付规则。重放固定具体输入及 attempt/batch，不重新选择“最新成功”，不隐式改源 |

`units` 可以来自来源元数据或**已核证且固定版本的映射定义**；两者冲突则拒绝。不能仅凭任意 JSON 中自报的单位、分页完成或样本数量批准正式消费。优先利用既有 Dataset 扩展、归档及诊断承载证据，不为每项不变量新建表。

完整度要求以**已冻结业务范围**为分母，不擅自扩大为全市场多年历史，也不能通过缩小请求范围逃避策略要求。上游没有总数时，必须说明替代的完整性证据及其局限；无法可靠确认必要覆盖就维持阻塞。

### 4.5 板块选择与成分供给：不让采集端预判结果

基线入口先选前 20 再要求成分恰好属于入选板块。[S4] v1.1 要求：Top-N、排序与同分规则仅由系统按已审核策略定义执行；“20”是基线行为，不由本计划替目标策略永久冻结。

Gate DS-FM 只选择符合实际来源的一种供给方式：

| 供给方式 | 执行要求 |
|---|---|
| 来源适合批量成分供给 | 原始完整响应留存；确认授权范围、身份、分类和日期后，由系统选择板块并提取所需成分。合法且在获准供给范围内的未入选记录可不参与结果；未知身份、非法范围和冲突仍拒绝 |
| 来源必须按板块查询成分 | 系统先冻结排行输入及目标策略，计算选择清单；采集端只按清单取成分，再回到同一输入版本完成结果。清单绑定排行 hash、策略身份、范围和日期；禁止取成分时改用新的“最新排行” |

按需方式只是一条固定用例，不建设通用 DAG。若既有 WorkBuddy 参数/合同不能安全承载系统生成的清单，须在 DS-FM 前记录为可实施性缺口并评审最小表达方式；**不能假定现有 1.0 已实现该两步交互，也不能伪造尚未产生的上游 StageResult。**批量方式已足够时不实现按需分支。

两种方式均不得修改已归档的原始 DataBundle 来伪装“来源只返回了入选子集”；应保存可追溯的内部业务投影。输入范围接受规则的变化必须进入版本化兼容审查，不能直接删除现有 fail-closed 校验。

### 4.6 目标策略身份与 evaluator 交接

策略主线的 [Slice 1C](invest-infra-candidate-strategies-mvp-plan-v1.0.md) 负责 v2.1.0 的业务范围、规则、审核、批准及对应 evaluator 交付；本计划负责所选数据路径与该版本的集成验收。交接只记录 artifact 引用与 hash、审核/批准记录、执行版本及测试位置，不新增注册表。

受控入口必须按既有策略 artifact 的哈希规则验证实际内容与审核对象一致，再交给纯计算；不能只比较 JSON 自报 hash，不能缺失时补一个预期 hash，也不能让字段变化后继续挂旧身份。复用既有可信加载能力，若入口尚未接入则进行局部接线；不得创建第二个策略身份权威。

基线 v2.0.0 及其历史结果保留；不静默改变公式、权重或历史 hash。目标范围、规则或 profile 发生改变，须通过策略主线确认新的不可变身份。characterization tests 用于识别变化，不能把现有不安全的输入接受行为冻结为生产承诺。

DS-0M 的技术核证可与策略治理并行；DS-C0/DS-1 对目标字段的最终接线依赖已冻结的策略数据要求。**DS-2 必须拿到已审核且获准用于影子的 v2.1.0 artifact、匹配的 evaluator 实现与测试证据；策略保持 inactive。**仅有旧版本探针或计算结果，不能作为目标版本的最终验收。

### 4.7 两次真实采集与确定性重放分开验收

| 验证动作 | 固定内容 | 判定方式 |
|---|---|---|
| 两次独立真实 shadow run | 每次各自记录获准来源、业务范围、日期/时点、版本和调用边界 | 均完成必要覆盖并归档；第二次不能只是复用第一次归档冒充新采集 |
| 每次归档的离线重放 | 原请求、原始/规范化输入、策略 artifact、映射及 evaluator 版本 | 不访问网络；得到相同规范化业务输入与确定性结果 |
| 同一请求上下文重放 | 上述内容及原 `request_id` | 沿用既有 StageResult 规范，比较完整结果及 hash |
| 不同请求但业务输入相同 | 相同业务内容和计算版本，运行身份可以不同 | 按预先声明的业务投影比较；不要求包含不同 request_id 的完整结果 hash 相同 |

不修改既有 hash 含义，也不为本轮新建通用哈希体系。应区分原始 artifact hash、规范化业务内容 hash/比较口径及运行结果 hash；映射或规则变更后保留旧结果，重新登记并验收新版本。

记录调用次数、实际耗时、失败/成功次数、样本覆盖和人工复核量；两次运行只能说明本次样本内表现，不宣称统计意义上的长期成功率、SLA 或策略有效性。具体采集日期、时段和允许成本由 Gate 记录事先明确，不在本计划编造统一阈值。

## 5. 范围

### 5.1 纳入

保留两个业务 Dataset 的贡献矩阵与来源核证；只实现一条入选路径；修补该路径必要的单位、完整度、范围、lineage 和可信入口；复用现有归档、evaluator、测试和运行结果；完成两次真实影子运行及各自重放。

策略新版本审核和对应规则实现由策略主线交付，本计划只验收交接结果；同一 evaluator 文件需要两条主线协作时，由一个已授权执行切片串行修改，不并发改写或重复验收同一职责。

### 5.2 明确不做

- 不建设 DatasetSupplyEngine、Source Policy 平台、通用组装器、评分/选源优化、审批后台或通用工作流；不同时实现 WorkBuddy/Provider 双路径或未入选来源的测试替身。
- 不默认升级协议 2.0、拆分四个 key、添加跨 Provider 自动 fallback 或正式 CrossCheckReport 持久化。
- 不迁移全部 Provider，不改造全系统质量治理，不加入市场宽度、零分母专项、跨日情绪、回测、收益验证或参数寻优。
- 不引入 AI 数据补全、动态策略解释器、自动策略批准/激活、自动交易或订单管理；不恢复 JiuwenSwarm 依赖。
- 不把 `vibe-astock` 或其他参考项目当成新执行主线；只有其线索能关闭本计划具体缺口时，才纳入 DS-0M 核证。

## 7. 依赖顺序与跨计划交接

```text
候选策略 Slice 1C-A：目标数据要求冻结 → 已审核、获准影子的 v2.1.0 + matching evaluator
                         │ DS-FM/接线前交接要求       │ DS-2 前交接实现
既有证据与实现 → DS-0M → DS-FM → DS-C0 差异验收 → DS-1 → DS-2 → B2A
                                                                │
策略治理获批 + B2A + 独立发布/激活授权 → Slice 1C-B → Slice 2 正式两阶段执行
  → Candidate（invest-infra）→ 内部 Admission → Evidence → Research → Timeline
  → Stage 4D Gate 3 → 后续计划按各自前置条件重新授权
```

本节只定义交接，不建立第二套准入状态、来源矩阵或总项目计划。职责对应如下：

| 交付 | 唯一负责位置 | 交接时点与证据 |
|---|---|---|
| 来源决定、两个业务输入及其采集映射 | 本计划 DS-FM / B2A | 对应 Gate 的原始证据、批准范围与适用条件；历史决定按差异复核 |
| 目标数据要求、v2.1.0 可信 artifact、对应 evaluator | [候选策略计划](invest-infra-candidate-strategies-mvp-plan-v1.0.md) Slice 1C-A | 要求在 DS-FM/相关接线前冻结；已审核且获准影子的 artifact、实现与测试在 DS-2 前交付，保持 inactive |
| 单一路径接入与影子验收 | 本计划 DS-C0 / DS-1 / DS-2 | 复用已有实现；两次真实采集及各自离线重放，不创建正式 Candidate |
| 发布/激活与正式两阶段 Candidate | 候选策略计划 Slice 1C-B / Slice 2 | 策略治理及 B2A 均通过后独立授权；实际策略、输入、StageResult 与 Candidate 身份可读回 |
| Admission → Research → Timeline 及下游追溯 | [Stage 4D 计划](invest-infra-stage4d-mvp-phased-execution-plan-v1.0.md) Gate 3 | 持久化及既有只读接口验证，不以影子 JSON 或归档成功代替正常主链路验收 |
| 研究中心、反馈闭环与运行观察 | [归档索引](archive/README.md) 的恢复要求 | 保持延期；各自前置和授权满足后消费前述事实，不由本计划提前建设 |

同一 evaluator 文件按授权任务串行修改：策略主线负责规则/版本，来源主线负责输入适配与集成，测试证据按职责复用。不形成“B2A 后才实现目标 evaluator、但 B2A 又等待它”的循环。策略/数据要求变化时只复核受影响部分，不自动重开所有已完成 Gate。

以下用例只落到本轮实际受影响入口，不建设跨全系统测试平台。预期结果属于 v1.1 要求，不能把本表当作已有测试通过记录。

| 未知板块、跨分类误配、重复或不明证券身份 | 拒绝；不按名称合并或静默去重修复 | 身份校验 |

| 单日响应与混合日期、缺少真实时点、跨日交付边界 | 依来源保证及已审核时间口径处理；不能将请求日期当来源证明 | 时间/交付校验 |
| artifact 内容变了但自报 hash 未变、错版本或未获准影子身份 | 受控入口拒绝；可信验证不能靠默认固定 hash | 策略可信加载/交接 |
