## 一、交易日判断逻辑（trading_day.py）

### 🔴 P0-01：节假日日历缺失
- **位置**: `trading_day.py:34-36`
- **问题**: `is_trading_day()` 仅检查周末，**未接入任何中国 A 股节假日日历**。春节、国庆等长假会被误判为交易日。
- **影响**: 非交易日自动生成报告，推送无效数据，浪费资源并误导用户。
- **修复建议**: 
  - 短期：硬编码未来 1 年节假日列表（`HOLIDAYS = {"2026-02-17", ...}`）
  - 长期：接入 akshare/tushare 的交易日历 API，或维护本地 `trade_calendar` 表

### 🟡 P1-01：长假回溯不足
- **位置**: `trading_day.py:54-60`
- **问题**: `get_last_trading_day()` 最多回溯 7 天。春节/国庆等 8 天长假时，无法找到上一交易日，直接返回原日期（非交易日）。
- **影响**: 节后首日盘前报可能使用错误日期数据。
- **修复建议**: 将回溯上限从 7 天改为 15 天，或改用 `while not is_trading_day():` 循环直到找到有效交易日

### 🟡 P1-02：交易时间判断过于宽泛
- **位置**: `trading_day.py:82-83`
- **问题**: `is_trading_time()` 仅检查 `9 <= hour < 15`，**未考虑午间休市（11:30-13:00）**。午休时段会被误判为交易时间。
- **影响**: 盘中异动检测在午休时可能触发无效告警。
- **修复建议**: 
  ```python
  if (9 * 60 <= time_val < 11 * 60 + 30) or (13 * 00 <= time_val < 15 * 00):
      return True
  ```

### 🟡 P2-01：交易阶段边界遗漏
- **位置**: `trading_day.py:109-133`
- **问题**: `get_trading_phase()` 在 00:00-08:59 时段返回 `"closed"`，但此时间段应标记为 `"pre_market_before_open"`（盘前准备期），与真正的休市区分。
- **影响**: 凌晨定时任务无法区分"还没开盘"和"已收盘"两种状态。
- **修复建议**: 增加 `06:00-09:00` 为 `"pre_market_preparation"` 阶段

## 二、四大报告类型业务逻辑

### 🔴 P1-02：盘前报节后首日回退策略不健壮
- **位置**: `pre_market.py:303-314`
- **问题**: 当 snapshot 全缺失时，自动回退到上一交易日。但如果上一交易日也是非交易日（如连续两个休市日），`get_last_trading_day()` 可能返回错误日期。且回退后**未通知用户数据已降级**。
- **影响**: 节后首日报告使用过期数据，用户无法察觉。
- **修复建议**: 
  - 增加回退深度检查（最多回退 N 天）
  - 在报告中明确标注"数据来自 X 月 X 日（非当日快照）"

### 🟡 P1-03：盘前报 memo 解析正则脆弱
- **位置**: `pre_market.py:44-159`（多个 `_parse_*_from_md` 方法）
- **问题**: 所有 WOA memo 数据通过正则表达式从 Markdown 文本中提取。正则模式硬编码，**一旦 WOA 输出格式微调即全部失效**。且无单元测试覆盖边界情况。
- **影响**: WOA 格式变更会导致整份报告数据为空或错误。
- **修复建议**: 
  - 将解析逻辑改为结构化解析（如 YAML/JSON 优先）
  - 为每个 `_parse_*` 方法添加单元测试

### 🟡 P1-04：盘前报 Step 2 代码重复
- **位置**: `pre_market.py:319-331`
- **问题**: `results = {}` 和 `cache_misses = []` 被声明两次（第 320-321 行和第 324 行），且注释说明与实际行为不一致（注释说"DB 未命中用降级数据，不触发 MCP"，但代码中 cache miss 时返回空字典 `{}` 而非 `FALLBACK_DATA`）。
- **影响**: 代码可读性差，后续维护者可能误改。
- **修复建议**: 删除重复声明，统一使用 `FALLBACK_DATA` 模式

### 🟡 P2-02：午盘报策略信号和 ETF 数据硬编码为空
- **位置**: `midday.py:226-232`
- **问题**: `_extract_strategy_realtime()` 和 `_extract_etf_intraday()` 直接返回空结构，**日志记录"暂未接入"但无降级方案**。午盘报缺少策略方向和 ETF 溢价率数据。
- **影响**: 午盘报核心板块（策略方向、ETF 监控）始终为空。
- **修复建议**: 
  - 从 DB 缓存的 `etf_alpha_signals` 表读取盘中快照
  - 或复用盘前报的策略信号数据

### 🟡 P2-03：盘后报 ETF 套利查询表不一致
- **位置**: `post_market.py:259-291`
- **问题**: `_extract_etf_arbitrage()` 从 `etf_alpha_signals` 表查询，但盘前报的 `_extract_etf_arbitrage()` 从 `etf_quotes` 表查询。**同一功能在不同报告中查不同表**，数据口径不一致。
- **影响**: 用户在同一天的盘前报和盘后报中看到矛盾的 ETF 套利信号。
- **修复建议**: 统一使用 `etf_quotes` 表作为 ETF 套利数据的唯一来源

### 🟡 P2-04：盘中异动 MCP 工具名映射缺失
- **位置**: `intraday_alert.py:40-43` vs `mcp_client.py:21-49`
- **问题**: 盘中异动直接调用 `limit_events`、`limit_down`、`anomaly_detection`，但 `MCP_TOOLS` 映射表中这些工具名**未做映射**（即直接使用原名）。如果 MCP 服务端工具名变更，此处无中间层保护。
- **影响**: MCP 工具名变更时，盘中异动模块需直接修改代码。
- **修复建议**: 在 `MCP_TOOLS` 中显式定义这些工具的映射关系

## 三、数据流程（采集→处理→格式化→推送）

### 🟡 P1-05：数据流缺少完整性校验
- **位置**: `report_engine.py:68-86`
- **问题**: `_fetch_data()` → `format_report()` → `db.save_report()` → `_send_to_qq()` 流程中，**未检查数据获取是否成功**。即使所有数据源都返回空/降级数据，报告仍会生成并推送。
- **影响**: 用户收到内容为空的"🔲 数据待接入"报告，无法区分"正常无信号"和"数据故障"。
- **修复建议**: 
  - 在 `format_report()` 后检查有效板块数量
  - 如果有效板块 < N 个，标记为"数据异常"并告警

### 🟡 P1-06：QQ 推送失败不影响报告保存但无重试
- **位置**: `report_engine.py:150-159`
- **问题**: QQ 推送失败时仅记录日志，不重试。如果推送通道临时故障（网络抖动），报告将永久丢失。
- **影响**: 关键市场报告可能因短暂网络问题无法送达。
- **修复建议**: 
  - 增加最多 3 次重试（指数退避）
  - 连续失败时写入本地文件作为兜底

### 🟢 P2-05：formatter 消息拆分可能截断 Markdown
- **位置**: `formatters.py:68-88`
- **问题**: `split_messages()` 按行拆分，**可能在 Markdown 语法中间截断**（如 `[text](url)` 被拆成两行）。
- **影响**: 推送的消息中链接失效或格式错乱。
- **修复建议**: 在段落边界（空行）处拆分，而非任意行

## 四、降级策略

### 🟡 P1-07：DB 缓存 `get_or_mcp()` 方法未实现降级逻辑
- **位置**: `market_data_cache.py:90-105`
- **问题**: `get_or_mcp()` 方法注释说"DB 无数据则降级走 MCP"，但实际**只返回 None**，由调用方决定是否走 MCP。而所有调用方（pre/mid/post market）在 cache miss 时都使用空字典或 FALLBACK_DATA，**从未真正触发 MCP**。
- **影响**: 注释与实际行为严重不符，`get_or_mcp()` 方法形同虚设。
- **修复建议**: 
  - 方案 A：删除 `get_or_mcp()` 方法，统一在调用方处理
  - 方案 B：实现真正的降级逻辑，接收 MCP client 参数并执行调用

### 🟡 P2-06：盘前报 fallback 数据不完整
- **位置**: `pre_market.py:329-330`
- **问题**: cache miss 时返回空字典 `{}`，而午盘/盘后报使用预定义的 `FALLBACK_DATA`（包含完整的嵌套结构）。**三种报告类型的降级策略不一致**。
- **影响**: 盘前报在数据缺失时更容易触发 formatter 的 KeyError。
- **修复建议**: 为盘前报也定义 `FALLBACK_DATA`，与午盘/盘后报保持一致

### 🟢 P3-01：MCP 降级结果结构可能不兼容
- **位置**: `mcp_client.py:164-172`
- **问题**: `_fallback_result()` 返回 `{"error": True, "data": None}`，但调用方（如 `pre_market.py`）期望的数据结构是嵌套字典。如果调用方直接访问 `result["content"][0]["text"]` 会崩溃。
- **影响**: MCP 降级时可能引发二次异常。
- **修复建议**: 在 `_fallback_result()` 中返回与正常结果兼容的结构

## 五、错误处理和边界情况

### 🔴 P0-02：数据库操作全部为占位实现
- **位置**: `db.py:16-136`
- **问题**: `Database` 类所有方法都是 TODO 占位，`save_report()` 固定返回 1，`get_report()` 固定返回 None，`is_duplicate_alert()` 固定返回 False。
- **影响**: 
  - 报告无法持久化存储
  - 盘中异动告警无去重机制，可能重复推送
  - 订阅功能完全不可用
- **修复建议**: 尽快实现真实的数据库操作（SQLite/PostgreSQL）

### 🟡 P1-08：异常处理过于宽泛
- **位置**: 多处 `except Exception as e: logger.warning(...)` 
- **问题**: 所有模块使用统一的 `except Exception` 捕获，**吞掉所有异常并仅记录日志**。调用方无法区分"数据为空"和"程序错误"。
- **影响**: 生产环境难以定位问题根因。
- **修复建议**: 
  - 定义自定义异常类（`DataFetchError`, `ParseError`, `DBError`）
  - 在关键路径上区分处理

### 🟡 P2-07：日期类型不一致
- **位置**: `report_engine.py:45-48` vs `trading_day.py:17`
- **问题**: `ReportEngine.__init__()` 接受 `trade_date` 为字符串，但 `is_trading_day()` 和 `get_last_trading_day()` 期望 `date` 对象。多处存在类型转换（`str ↔ date`），容易出错。
- **影响**: 日期处理逻辑分散且不一致。
- **修复建议**: 统一内部使用 `date` 对象，仅在 CLI 入口做字符串转换

### 🟢 P3-02：MCP Token 硬编码
- **位置**: `mcp_client.py:18`
- **问题**: MCP API Token 直接硬编码在源码中。如果代码仓库泄露，Token 将被暴露。
- **影响**: 安全风险（API 配额被滥用）。
- **修复建议**: 从环境变量或密钥管理服务读取

### 🟢 P3-03：`_get_cache` 方法签名不一致
- **位置**: `report_engine.py:136-138`
- **问题**: `_get_cache()` 接受 `trade_date: str` 参数，但其他方法（如 `_fetch_pre_market`）传入的是 `self.trade_date`（`date` 对象）。Python 动态类型不会报错，但语义混乱。
- **影响**: 代码可读性差。
- **修复建议**: 统一参数类型为 `str` 或 `date`

## 八、审计结论

汇报模块整体架构设计合理（DB 优先 + MCP 降级），四种报告类型的业务逻辑基本完整。但存在以下**关键风险**：

1. **交易日判断严重依赖周末检查**，节假日缺失是最高优先级问题
2. **数据库操作全部未实现**，导致报告无法持久化、告警无去重
3. **降级策略不一致**，三种报告类型的 fallback 行为不同，增加维护成本
4. **数据完整性校验缺失**，空报告可能被推送给用户

建议优先修复 P0/P1 级别问题，确保系统在节假日和异常场景下的正确性。
