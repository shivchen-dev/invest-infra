## 二、P0 致命问题（必须立即修复）

### 2.1 数据库操作全部为占位实现

**跨维度**: 逻辑 ⚠️ | 数据源 🔴 | 架构 🔴

- **位置**: `db.py:16-136`
- **问题**: `Database` 类所有方法都是 TODO 占位，`save_report()` 固定返回 1，`get_report()` 固定返回 None，`is_duplicate_alert()` 固定返回 False。
- **影响**:
  - 报告无法持久化存储
  - 盘中异动告警无去重机制，可能重复推送
  - 订阅功能完全不可用
  - 系统重启后所有报告丢失
- **修复建议**: 接入真实 PostgreSQL 数据库，创建 `market_reports` 和 `intraday_alerts` 表实现完整 CRUD 操作

### 2.2 节假日日历缺失

**跨维度**: 逻辑 🔴 | 架构 🟡

- **位置**: `trading_day.py:34-36`
- **问题**: `is_trading_day()` 仅检查周末，**未接入任何中国 A 股节假日日历**。春节、国庆等长假会被误判为交易日。
- **影响**: 非交易日自动生成报告，推送无效数据，浪费资源并误导用户
- **修复建议**:
  - 短期：硬编码未来 1 年节假日列表
  - 长期：接入 akshare/tushare 的交易日历 API，或维护本地 `trade_calendar` 表

### 2.3 MCP Token 硬编码

**跨维度**: 逻辑 🟡 | 数据源 🟡 | 架构 🔴 | 代码质量 🔴

- **位置**: `mcp_client.py:18`
- **问题**: MCP API Token 直接硬编码在源码中。如果代码仓库泄露，Token 将被暴露。
- **影响**: 安全风险（API 配额被滥用）
- **修复建议**: 从环境变量或密钥管理服务读取

### 2.4 盘中异动告警无去重机制

**跨维度**: 逻辑 🔴 | 数据源 🟡

- **位置**: `intraday_alert.py` + `db.py:is_duplicate_alert()`
- **问题**: `is_duplicate_alert()` 始终返回 False（占位实现），同一股票在同一时段内的异动告警会被重复推送
- **影响**: 用户收到重复告警，降低系统可信度
- **修复建议**: 实现真正的去重逻辑（基于 stock_code + alert_type + time window）

## 三、P1 高优先级问题

### 3.1 盘前报降级策略不完整

**跨维度**: 逻辑 🟡 | 数据源 🔴

- **位置**: `pre_market.py:329-330`
- **问题**: cache miss 时返回空字典 `{}`，而午盘/盘后报使用预定义的 `FALLBACK_DATA`（包含完整的嵌套结构）。三种报告类型的降级策略不一致。
- **影响**: 盘前报在数据缺失时更容易触发 formatter 的 KeyError
- **修复建议**: 为盘前报也定义 `FALLBACK_DATA`，与午盘/盘后报保持一致

### 3.2 PreMarketReporter 严重膨胀

**跨维度**: 架构 🔴 | 代码质量 🟡

- **位置**: `modules/pre_market.py`
- **问题**: 代码达 **1105 行**，承担了数据获取、数据解析、业务推导三重职责，违反单一职责原则
- **影响**: 难以维护、测试和复用
- **修复建议**: 拆分为 `MemoParser` / `DataExtractor` / `Reporter` 三层

### 3.3 数据流缺少完整性校验

**跨维度**: 逻辑 🟡 | 数据源 🟡

- **位置**: `report_engine.py:68-86`
- **问题**: `_fetch_data()` → `format_report()` → `db.save_report()` → `_send_to_qq()` 流程中，未检查数据获取是否成功。即使所有数据源都返回空/降级数据，报告仍会生成并推送。
- **影响**: 用户收到内容为空的"🔲 数据待接入"报告，无法区分"正常无信号"和"数据故障"
- **修复建议**: 在 `format_report()` 后检查有效板块数量，如果有效板块 < N 个，标记为"数据异常"并告警

### 3.4 QQ 推送无重试机制

**跨维度**: 逻辑 🟡 | 数据源 🟡

- **位置**: `report_engine.py:150-159`
- **问题**: QQ 推送失败时仅记录日志，不重试。如果推送通道临时故障（网络抖动），报告将永久丢失。
- **影响**: 关键市场报告可能因短暂网络问题无法送达
- **修复建议**: 增加最多 3 次重试（指数退避），连续失败时写入本地文件作为兜底

### 3.5 长假回溯不足

**跨维度**: 逻辑 🟡 | 架构 🟡

- **位置**: `trading_day.py:54-60`
- **问题**: `get_last_trading_day()` 最多回溯 7 天。春节/国庆等 8 天长假时，无法找到上一交易日，直接返回原日期（非交易日）
- **影响**: 节后首日盘前报可能使用错误日期数据
- **修复建议**: 将回溯上限从 7 天改为 15 天

### 3.6 get_or_mcp() 方法未实现降级逻辑

**跨维度**: 逻辑 🟡 | 数据源 🟡

- **位置**: `market_data_cache.py:90-105`
- **问题**: `get_or_mcp()` 方法注释说"DB 无数据则降级走 MCP"，但实际只返回 None，由调用方决定是否走 MCP。而所有调用方在 cache miss 时都使用空字典或 FALLBACK_DATA，从未真正触发 MCP
- **影响**: 注释与实际行为严重不符，方法形同虚设
- **修复建议**: 删除 `get_or_mcp()` 方法，统一在调用方处理

## 四、P2 中优先级问题

### 4.1 午盘报策略信号和 ETF 数据硬编码为空

- **位置**: `midday.py:226-232`
- **问题**: `_extract_strategy_realtime()` 和 `_extract_etf_intraday()` 直接返回空结构，午盘报核心板块（策略方向、ETF 监控）始终为空
- **修复建议**: 从 DB 缓存的 `etf_alpha_signals` 表读取盘中快照

### 4.2 盘后报 ETF 套利查询表不一致

- **位置**: `post_market.py:259-291` vs `pre_market.py`
- **问题**: 同一功能在不同报告中查不同表（`etf_alpha_signals` vs `etf_quotes`），数据口径不一致
- **修复建议**: 统一使用 `etf_quotes` 表

### 4.3 交易时间判断未考虑午间休市

- **位置**: `trading_day.py:82-83`
- **问题**: `is_trading_time()` 仅检查 `9 <= hour < 15`，未考虑午间休市（11:30-13:00）
- **修复建议**: 增加午休时段判断

### 4.4 缺少抽象基类

- **位置**: 整体架构
- **问题**: 四个 Reporter 类没有共同的抽象基类，新增报告类型需修改多处代码（违反开闭原则）
- **修复建议**: 定义 `BaseReporter` 抽象基类

### 4.5 sys.path.insert 反模式

- **位置**: `report_engine.py:21`
- **问题**: 动态修改 `sys.path` 破坏模块导入的可预测性
- **修复建议**: 使用 Python 包结构 + `python -m reports.report_engine` 方式运行

### 4.6 全局单例过多

- **位置**: `db.py`, `mcp_client.py`, `qq_push.py`
- **问题**: 难以进行单元测试，多线程环境下可能存在竞态条件
- **修复建议**: 使用依赖注入容器或配置类管理全局状态

### 4.7 formatter 消息拆分可能截断 Markdown

- **位置**: `formatters.py:68-88`
- **问题**: 按行拆分可能在 Markdown 语法中间截断（如 `[text](url)` 被拆成两行）
- **修复建议**: 在段落边界（空行）处拆分

### 4.8 异常处理过于宽泛

- **位置**: 多处 `except Exception as e: logger.warning(...)`
- **问题**: 吞掉所有异常并仅记录日志，调用方无法区分"数据为空"和"程序错误"
- **修复建议**: 定义自定义异常类（`DataFetchError`, `ParseError`, `DBError`）

### 4.9 DB 连接管理性能问题

- **位置**: `market_data_cache.py` + `loader.pg`
- **问题**: 每次查询都创建/关闭连接，高频调用时可能产生连接开销；`has_all()` 方法存在 N+1 查询问题
- **修复建议**: 使用连接池，改为批量查询

## 九、结论

汇报模块整体架构设计合理，数据流清晰。主要风险集中在：

1. **基础设施未完成**: db.py 占位实现、节假日日历缺失
2. **安全性漏洞**: MCP Token 硬编码
3. **代码规模失控**: PreMarketReporter (1105行) 和 Formatters.py (950行) 严重膨胀
4. **扩展性不足**: 新增报告类型需修改多处代码

**建议优先完成 Phase 1 的基础加固，确保系统在节假日和异常场景下的正确性。**
