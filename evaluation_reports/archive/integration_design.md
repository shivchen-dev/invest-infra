## 1. 执行摘要

本报告基于 data-architect 对现有 Morning Briefing 的架构分析，以及 tech-expert 对新汇报模块的技术评估，提出三种整合方案并进行对比分析。

**核心结论：推荐方案 A（完全独立运行）+ 渐进式演进路径**

理由：
1. 现有 Morning Briefing 架构稳定，不宜大改
2. 新模块设计已完成，有自己的数据管道和数据库表
3. 两种模式（AI Agent vs 脚本规则）适用场景不同，强行整合反而增加复杂度
4. 仅共享基础设施层，保持业务逻辑隔离

## 2. 混合架构设计说明

### 2.1 两种模式的职责划分

| 模式 | 适用场景 | 代表汇报 | 数据源 | 执行方式 |
|------|---------|---------|--------|---------|
| **AI 智能体模式** | 需综合研判、跨维度推理、情景假设 | Morning Briefing（盘前洞察） | 本地 PG + RssCast MCP | 多 Agent 协作（WOA → CIA） |
| **脚本规则模式** | 规则化数据聚合、固定模板、异动监控 | 盘前报/午盘报/盘后报/盘中轮询 | wudao_aStock MCP | 单脚本执行（report_engine.py） |

### 2.2 整合原则

1. **形式独立，逻辑整合** — Morning Briefing 保持现有 AI 模式，新增模块用脚本规则模式
2. **共享基础设施** — QQ 推送通道、数据库（PG/Redis）、节假日判断逻辑
3. **数据源双轨策略** — 本地 PG 为主，MCP 为辅，按需切换

## 3. 三种整合方案对比

### 3.1 方案 A：完全独立运行（推荐）

**架构描述：**
- Morning Briefing（AI 模式）与 新汇报模块（脚本模式）各自独立
- 仅共享基础设施层（Redis/PG/QQ）
- 业务逻辑完全隔离，互不影响

**优点：**
| 维度 | 说明 |
|------|------|
| **隔离性** | 两个系统完全独立，一个故障不影响另一个 |
| **维护成本** | 低，各自维护自己的代码和配置 |
| **实施难度** | 最低，无需改造现有流程 |
| **风险等级** | 低，现有 Morning Briefing 运行稳定 |

**缺点：**
| 维度 | 说明 |
|------|------|
| **数据一致性** | 高，两个系统使用不同数据源（PG vs MCP），可能导致同一天的数据出现矛盾 |
| **维护成本** | 中，两套数据管道需要分别维护 |
| **功能重叠** | 盘前报的【宏观环境】【强势行业】【情绪温度计】与 Morning Briefing 高度重叠 |

**工作量估算：** 0h（无需改造，直接部署新模块）

### 3.2 方案 B：复用 Morning Briefing 的数据采集层

**架构描述：**
- 新汇报模块复用本地 PG 数据
- 但午盘报/盘后报需要的数据（如 concept_ranking、capital_flow）Morning Briefing 不采集
- 需要扩展 PG 表结构，新增数据采集管道

**优点：**
| 维度 | 说明 |
|------|------|
| **数据一致性** | 低，统一使用 PG 数据源 |
| **维护成本** | 中，共享数据采集层 |
| **实施难度** | 中，需扩展 PG 表结构 |

**缺点：**
| 维度 | 说明 |
|------|------|
| **数据覆盖不完整** | Morning Briefing 不采集 concept_ranking、capital_flow、limit_up_ladder 等数据 |
| **实施成本高** | 需要新增数据采集管道，工作量约 8-10h |
| **耦合度高** | 新模块依赖 Morning Briefing 的数据采集逻辑 |

**工作量估算：** 8-10h（扩展 PG 表 + 新增数据采集管道）

### 3.3 方案 C：Morning Briefing 作为新模块的盘前报实现

**架构描述：**
- 将 Morning Briefing 定位为"盘前报"的 AI 增强版
- 新汇报模块的 report_engine.py 统一管理所有汇报类型的生成和推送
- 盘前报通过调用 Morning Briefing 流程实现（WOA → CIA）

**优点：**
| 维度 | 说明 |
|------|------|
| **架构统一** | 所有汇报类型由 report_engine.py 统一管理 |
| **数据复用最大化** | Morning Briefing 的 PG 数据直接复用 |
| **维护成本** | 低，单一入口管理所有汇报 |

**缺点：**
| 维度 | 说明 |
|------|------|
| **耦合度高** | 改造现有流程风险大，可能影响 Morning Briefing 稳定性 |
| **实施难度** | 最高，需重构 report_engine.py 支持 AI Agent 模式 |
| **工作量** | 最大，约 15-20h |

**工作量估算：** 15-20h（重构 + 测试 + 迁移）

### 3.4 方案对比汇总表

| 维度 | 方案 A（完全独立） | 方案 B（复用 PG） | 方案 C（Morning Briefing 子模块） |
|------|-------------------|------------------|--------------------------------|
| **架构复杂度** | 低 | 中 | 高 |
| **数据一致性风险** | 高（双数据源矛盾） | 低（统一 PG） | 最低（完全复用） |
| **实施成本** | 最低（0h） | 中（8-10h） | 最高（15-20h） |
| **维护成本** | 中（两套管道） | 中（共享采集层） | 低（统一引擎） |
| **风险等级** | 低（隔离好） | 中（数据覆盖缺口） | 高（耦合深） |
| **推荐指数** | ⭐⭐⭐⭐⭐ | ⭐⭐⭐ | ⭐⭐ |

## 4. 推荐结论及理由

### 4.1 推荐方案：方案 A（完全独立运行）+ 渐进式演进

**核心决策：** 短期采用方案 A，长期根据 MCP 稳定性逐步演进到方案 C。

### 4.2 推荐理由

#### 理由 1：现有 Morning Briefing 架构稳定，不宜大改
- data-architect 分析显示，Morning Briefing 经过生产验证，运行稳定
- 改造风险高，可能影响现有投研流程
- "如果没坏，就不要修"原则

#### 理由 2：新模块设计已完成，有自己的数据管道
- tech-expert 评估显示，新汇报模块的 technical_design.md 已完整定义
- report_engine.py + 模块化 reporters 架构清晰
- 无需依赖 Morning Briefing 即可独立运行

#### 理由 3：两种模式适用场景不同，强行整合增加复杂度
- AI Agent 模式适合需要综合研判的场景（Morning Briefing）
- 脚本规则模式适合规则化数据聚合（新汇报模块）
- 混合架构方向要求"形式独立，逻辑整合"

#### 理由 4：渐进式演进降低风险
- 短期：方案 A 独立运行，验证 MCP 稳定性
- 中期：增加 AI 增强层，提升内容质量
- 长期：MCP 稳定后，逐步迁移到方案 C

### 4.3 渐进式演进路径

| 阶段 | 时间 | 目标 | 触发条件 | 工作量 |
|------|------|------|----------|--------|
| **阶段 1**（短期） | 0-2 周 | 方案 A：完全独立运行，共享 QQ 推送通道 | MCP 连续 30 天成功率 > 95% | 0h |
| **阶段 2**（中期） | 2-4 周 | 增加 AI 增强层，提升内容质量 | MCP 稳定性验证通过 | 2h |
| **阶段 3**（长期） | 4-8 周 | 方案 C：Morning Briefing 作为盘前报实现 | 数据一致性验证通过 | 15-20h |

## 5. 共享基础设施清单

基于 data-architect 和 tech-expert 的分析，以下组件可作为新汇报模块的共享基础：

| 组件 | 复用方式 | 注意事项 |
|------|----------|----------|
| **Redis Stream** | 可复用 task_queue/cia_task_queue 机制 | 需新增队列名称（如 report_queue） |
| **PostgreSQL** | 可复用 investdb 连接配置 | 建议新建专用表，不混用 investment_memos |
| **QQ Bot** | 复用 `_qq_notify()` 函数逻辑 | 新模块使用 QQ Channel 而非 QQ Bot |
| **节假日判断** | 需新增（现有系统无此功能） | cron 表达式限定 1-5 不够，需排除法定节假日 |
| **日志框架** | 可复用 print 日志模式 | 建议升级为结构化日志 |
| **交易日历 API** | 可复用 tushare/akshare 接口 | 缓存本地交易日历，减少 API 调用 |

## 6. 风险与约束评估

### 6.1 技术风险

| 风险 | 影响 | 缓解措施 | 责任人 |
|------|------|----------|--------|
| **MCP 单点故障** | 所有汇报类型瘫痪 | 实现请求队列 + 限流 + 指数退避重试（tech-expert P0） | tech-expert |
| **数据一致性矛盾** | 同一天数据出现矛盾 | 标注数据来源，允许用户选择查看哪个系统的数据 | system-architect |
| **intraday_alerts 去重缺失** | 重复告警 | 增加唯一约束：`UNIQUE KEY uk_stock_time (stock_code, alert_type, DATE(alert_time))` | tech-expert |
| **Cron 节假日判断缺失** | 节假日空跑 | 脚本内增加交易日判断逻辑（使用 tushare/akshare 交易日历 API） | tech-expert |
| **QQ 消息长度限制** | 长报告发送失败 | 设置每条消息最大 4000 字符，自动分片 | tech-expert |

### 6.2 架构约束

| 约束 | 说明 | 影响 |
|------|------|------|
| **混合架构方向** | CIA 要求"AI 智能体模式 + 脚本规则模式双轨" | 新模块需增加 AI 增强层（中期演进） |
| **数据源双轨策略** | 本地 PG 为主，MCP 为辅 | 新模块需实现 PG/MCP 切换逻辑 |
| **共享基础设施** | QQ 推送通道、数据库、节假日判断逻辑 | 需定义清晰的接口规范 |

### 6.3 实施约束

| 约束 | 说明 | 影响 |
|------|------|------|
| **现有 Morning Briefing 稳定性** | 不宜大改 | 短期采用方案 A，长期再考虑方案 C |
| **MCP 工具可用性** | wudao_aStock 稳定性未知 | 需验证 MCP 连续 30 天成功率 > 95% |
| **数据一致性验证** | 两个系统数据可能矛盾 | 需建立数据一致性监控机制 |

## 7. 最终建议

### 7.1 短期行动（0-2 周）

1. **部署新汇报模块**，采用方案 A（完全独立运行）
2. **共享 QQ 推送通道**，复用现有 QQBot 接口
3. **新增交易日判断逻辑**，避免节假日空跑
4. **实现 MCP 并发控制**，解决 P0 级风险

### 7.2 中期行动（2-4 周）

1. **增加 AI 增强层**，对盘前报/盘后报调用 LLM 生成自然语言总结
2. **建立数据一致性监控**，对比两个系统的数据差异
3. **实现错误隔离机制**，report_engine.py 支持"部分成功"策略

### 7.3 长期行动（4-8 周）

1. **评估方案 C 可行性**，如果 MCP 稳定且数据一致性好，可逐步迁移
2. **引入消息队列中间件**（如 RabbitMQ/Kafka），替代 Redis Stream
3. **扩展推送渠道**，支持微信/钉钉/Telegram 等多渠道
